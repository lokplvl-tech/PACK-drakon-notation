# Ключевые различения: нотация ДРАКОН

> Источник: FPF A.7 (Strict Distinction)
> Первоисточник содержания: В.Д. Паронджанов, «Как улучшить работу ума» (изд. «Дело», 2001) и рукопись «Язык ДРАКОН. Краткое описание» - через `DS-strategy/inbox/WP-7/drakon-knowledge-base.md`.

### DRK.D.001: Примитив ≠ силуэт
**Maturity:** seed

**Определение A (примитив):** простой алгоритм без веток - последовательность икон на одном шампуре, без именованных ответвлений.

**Определение B (силуэт):** сложный алгоритм, разбитый на именованные ветки - крупноблочное деление, дающее панорамный обзор структуры до чтения деталей.

**Тест:** «В схеме есть именованные ветки, читаемые как оглавление?» Есть - силуэт. Нет - примитив.

**Почему важно:** выбор формы - не стилистика, а прямое следствие сложности метода. Метод из нескольких независимых процедур, описанный как примитив, теряет то самое преимущество языка, ради которого он и придуман - панорамное восприятие структуры до вникания в детали (см. «три царских вопроса», `DRK.D.003`-соседние приёмы).

**SoTA:** `current`
- Критерий пересмотра: не ожидается - базовое деление языка, зафиксировано в первоисточнике.

### DRK.D.002: Главный маршрут ≠ побочный
**Maturity:** seed

**Определение A (главный маршрут):** путь к наибольшему успеху - идёт по крайней левой вертикали схемы (правило главного маршрута).

**Определение B (побочный маршрут):** менее успешные исходы - располагаются правее, упорядочены по убыванию успешности («чем правее, тем хуже»).

**Тест:** «Это путь наибольшего успеха или отклонение от него?» Наибольший успех - крайняя левая вертикаль. Отклонение - правее, тем дальше, чем хуже исход.

**Почему важно:** это не эстетическое расположение, а кодирующее правило - расположение на схеме само по себе несёт информацию о качестве исхода. Нарушение (произвольный порядок веток) убирает эту информацию и заставляет читателя анализировать каждую ветку заново, вместо того чтобы прочитать порядок с одного взгляда.

**Частая ошибка:** «рокировка» существует именно как приём для исправления этой ошибки - равносильный обмен местами плеч развилки, убирающий логическое отрицание и ставящий неудачный исход правее.

**SoTA:** `current`
- Критерий пересмотра: не ожидается - базовое правило языка.

### DRK.D.003: Схема как источник истины ≠ схема как рендер
**Maturity:** seed

**Определение A (схема как источник истины):** ДРАКОН-схема - первичный артефакт, из неё генерируется исполняемый код (например, экспорт в JavaScript через связку DrakonHub/DrakonTech).

**Определение B (схема как рендер):** метод уже описан текстово-табличным способом (структура `E.18` - позиции потока с гвардами); схема - визуальное представление той же логики для человеческого восприятия, код пишется отдельно и напрямую.

**Тест:** «Если стереть схему, теряется ли логика метода, или она остаётся в тексте?» Теряется - схема источник истины. Остаётся - схема рендер.

**Почему важно:** решает, оправдана ли кодогенерация в конкретном случае. Для формульных позиций `FE.M.001` (мебельный домен, связка с САПР «Базис-Салон») решение уже принято архитектурной оценкой - там нужен режим A. Для большинства методов в системе, уже описанных таблицей `E.18`, верен режим B: добавлять кодогенерацию поверх готового текстового описания - лишний слой без выигрыша.

**Последствия смешения:** если считать любую схему источником истины, начинается дублирование логики между таблицей метода и схемой - расхождение между ними становится вопросом времени.

**SoTA:** `current`
- Критерий пересмотра: пересматривается не сам язык, а решение по конкретному методу - каждый новый метод с высокой ценой ошибки заново проходит этот тест.

### DRK.D.004: Шампур-блок ≠ произвольная линия потока
**Maturity:** seed

**Определение A (шампур-блок):** формально определённая часть схемы - один вход сверху, один выход снизу, строго на одной вертикали.

**Определение B (произвольная линия потока):** любая последовательность действий, нарисованная как блок-схема без соблюдения этого требования - типично в обычных, не-ДРАКОН диаграммах.

**Тест:** «Вход и выход блока лежат строго на одной вертикальной линии?» Да - шампур-блок. Нет - это не ДРАКОН-схема, а просто рисунок, похожий на неё.

**Почему важно:** различение отделяет схему, подчинённую формальным правилам языка (и потому проверяемую на нарушения), от рисунка, который выглядит похоже, но не даёт ни одной из заявленных гарантий читаемости. Инструменты (DrakonHub и др.) поддерживают именно шампур-блоки - редактор физически не даёт нарисовать нарушение этого правила, что и есть источник заявленной «безошибочности» языка.

**SoTA:** `current`
- Критерий пересмотра: не ожидается - формальное требование языка.

### DRK.D.005: Икона «Вставка» ≠ обычная процедура
**Maturity:** seed

**Определение A (икона «Вставка»):** декомпозиция сложного алгоритма по правилам языка - приём «разрежь великана», вынос фрагмента с сохранением формальной связи (иконой «Адрес») с местом вызова.

**Определение B (обычная процедура/функция):** вынесение кода в отдельную единицу без обязательства следовать правилам шампура и силуэта внутри неё.

**Тест:** «Вынесенный фрагмент сам подчиняется правилам шампура и силуэта, с формальной адресной связью к точке вызова?» Да - икона «Вставка». Нет - это обычная процедура, ДРАКОН-правила на неё не распространяются автоматически.

**Почему важно:** без этого различения решение «когда дробить схему» превращается в интуитивное, тогда как язык даёт для этого точный приём (Три царских вопроса → если частей слишком много для одной «шапки» - разрезать и вставить).

**SoTA:** `current`
- Критерий пересмотра: не ожидается - приём языка, зафиксирован в первоисточнике.

### DRK.D.006: Икона «Адрес» ≠ произвольная стрелка
**Maturity:** seed

**Определение A (икона «Адрес»):** дисциплинированная передача управления - именованная связь между веткой/позицией-источником и веткой/позицией-приёмником, часть формального языка, проверяемая на корректность (нет висящих адресов, нет адресов в середину ветки).

**Определение B (произвольная стрелка):** линия, нарисованная от одного места схемы к другому без статуса формального элемента языка - типично для обычных блок-схем и майндмэпов.

**Тест:** «Эта связь - именованная икона языка с проверяемыми правилами (куда можно вести адрес, откуда) или просто нарисованная линия?» Икона - формальный элемент. Линия - не ДРАКОН-схема в строгом смысле.

**Почему важно:** без этого различения «адрес» на схеме легко принять за обычную стрелку перехода и нарушить её правила (например, направить в середину чужой ветки, а не в её начало - см. общий запрет входа в ветку не через начало). Именно адреса несут связь между вставками и точками вызова (`DRK.D.005`) и между ветками силуэта - если они не формальные, вся конструкция «шапка → ветки → адреса» (трёхэтапный метод познания схемы) перестаёт работать как заявлено.

**Происхождение:** перенесено из Пака «Визуализация алгоритмов» (`PACK-algorithm-visualization`, код AV) при слиянии дублирующих Паков 2026-08-01 - домен был случайно заведён дважды, содержание объединено здесь.

**SoTA:** `current`
- Критерий пересмотра: не ожидается - формальный элемент языка, зафиксирован в первоисточнике.
